11.4 Ключевые UX-сценарии

Сценарий A: «Создать и запустить проект»

  1. Пользователь нажимает «Новый проект» → открывается модальное окно
  2. Шаг 1: Имя, выбор платформы (TikTok/YT/IG), расписание (ежедневно в 10:00)
  3. Шаг 2: Выбор мира (Вьетнам) → автоматическая загрузка локаций
  4. Шаг 3: Выбор персонажей (Хранитель, Доктор Лин) → загрузка их конфигурации
  5. Шаг 4: Выбор стиля (Документальный тёплый) → предпросмотр
  6. Шаг 5: Кнопка «Генерировать идеи» → запуск Креативного директора → состояние загрузки с оценкой времени
  7. Результаты показаны карточками: свайп влево/вправо для просмотра, звезда для одобрения
  8. «Создать первое видео» → полный запуск пайплайна → прогресс-бар сверху

Сценарий B: «Проверить и исправить контент»

  1. Пользователь открывает проект → видит статус пайплайна: «ЭТАП 4: Генерация промптов»
  2. Когда этап завершён → появляется бейдж уведомления
  3. Пользователь нажимает «Проверить» → открывается раскадровка
  4. Каждая сцена показана карточкой: текст сценария → изображение → видео → кнопка редактирования
  5. Кнопка редактирования открывает встроенный редактор: можно изменить промпт, перегенерировать, сменить ракурс
  6. Кнопка «Принять всё» → переход к следующему этапу
  7. Финальный просмотр: видеоплеер → одобрить → запланировать публикацию → готово

Сценарий C: «Мониторинг и оптимизация»

  1. Вкладка аналитики показывает карточки производительности для каждого видео
  2. Сортировка по просмотрам / вовлечённости / репостам для поиска лидеров
  3. Клик по видео → детальная аналитика: график времени просмотра, разбивка вовлечённости, демография
  4. Панель рекомендаций AI: «Темы об уличной еде получают в 2.3x больше вовлечённости. Рекомендуем больше контента о еде.»
  5. Однокнопочное «Применить рекомендации» → обновление шаблонов промптов и предложений тем

Сценарий D: «Диаграмма переходов состояний публикации»

📄 Черновик (draft) → 📅 Запланировано (scheduled) → ⟳ Публикуется (publishing) → ✓ Опубликовано (published) → 📊 Сбор аналитики
⟳ Публикуется → ✗ Ошибка (failed) → 📄 Черновик (повтор)
⟳ Публикуется → ⟳ Повтор (retrying) → ⟳ Публикуется → ✗ Ошибка (макс. попыток)

12.5 Агент Оптимизации — Алгоритм анализа

Псевдокод еженедельного запуска Агента Оптимизации:

python
def optimize_project(project_id: str):
    # 1. Собрать все публикации за последние 7 дней
    pubs = get_publications(project_id, since=now() - 7_days)

    if len(pubs) < 3:
        return {"status": "insufficient_data", "message": "Нужно минимум 3 публикации"}

    # 2. Разделить на лучшие/худшие
    sorted_pubs = sorted(pubs, key=lambda p: p.engagement_rate, reverse=True)
    top_25 = sorted_pubs[:max(1, len(sorted_pubs)//4)]
    bottom_25 = sorted_pubs[-max(1, len(sorted_pubs)//4):]

    # 3. Анализ паттернов
    patterns = {
        "topics": analyze_pattern(top_25, bottom_25, lambda p: p.topic),
        "hooks": analyze_pattern(top_25, bottom_25, lambda p: p.hook_type),
        "formats": analyze_pattern(top_25, bottom_25, lambda p: p.format),
        "lengths": analyze_pattern(top_25, bottom_25, lambda p: p.duration),
        "hashtags": analyze_tag_pattern(top_25, bottom_25),
        "thumbnail_texts": analyze_pattern(top_25, bottom_25, lambda p: p.thumbnail_text_type),
        "ctas": analyze_pattern(top_25, bottom_25, lambda p: p.cta_type),
        "characters": analyze_pattern(top_25, bottom_25, lambda p: p.character_id),
        "worlds": analyze_pattern(top_25, bottom_25, lambda p: p.world_id)
    }

    # 4. Генерация рекомендаций
    recommendations = []
    for feature, analysis in patterns.items():
        if analysis.top_trait:
            recommendations.append({
                "feature": feature,
                "action": "emphasize",
                "value": analysis.top_trait,
                "impact": analysis.improvement_pct,
                "confidence": analysis.confidence
            })
        if analysis.underperforming_trait:
            recommendations.append({
                "feature": feature,
                "action": "reduce",
                "value": analysis.underperforming_trait,
                "impact": -analysis.decline_pct,
                "confidence": analysis.confidence
            })

    # 5. Автоматическое применение
    for rec in recommendations:
        if rec["confidence"] > 0.7 and rec["action"] == "emphasize":
            update_project_settings(project_id, rec)

    return {"recommendations": recommendations, "applied": count_applied}

12.6 Проекция на 2029: Real-Time ClickHouse Аналитика на 100K Enterprise

ПРОГНОЗИРУЕМОЕ УЗКОЕ МЕСТО: PostgreSQL не выдержит >1M строк

Почему это важно сейчас: На этапе MVP PostgreSQL справляется, но при 1M+ строк аналитические запросы займут 30+ секунд. Агрегационные запросы заблокируют запись пайплайна. Мы закладываем ClickHouse с первого дня, чтобы миграция была бесшовной.

Архитектурное решение: Все данные производительности стримятся в реальном времени от Publisher Agent напрямую в ClickHouse через Kafka/Redpanda. Дашборд читает данные исключительно из ClickHouse. Состояние пайплайна читает из ScyllaDB.

Агент Оптимизации эволюционирует с Reinforcement Learning from AI Feedback (RLAIF) на глобальном масштабе:

V1 (Статические правила)V2 (Глобальный RLAIF)

V2 RLAIF Алгоритм оптимизации (Temporal.io Workflow):

Workflow: GlobalOptimizationLoop {
    every(6 hours) {
        // 1. Собрать top 0.1% исполнителей по ВСЕМ тенантам
        global_winners = clickhouse.query("""
            SELECT prompt_hash, template_id, avg(engagement_rate) as er
            FROM analytics.mv_daily_metrics
            WHERE publish_date >= now() - INTERVAL 1 DAY
              AND total_views > 1000
            GROUP BY prompt_hash, template_id
            ORDER BY er DESC
            LIMIT 100
        """)

        // 2. Извлечь общие латентные признаки
        features = extract_latent_patterns(global_winners)

        // 3. Сгенерировать улучшенный вариант шаблона промпта
        new_template = prompt_generator.refine(features)

        // 4. Развернуть как A/B кандидата (5% трафика)
        prompt_registry.deploy_candidate(new_template, traffic_weight=0.05)

        // 5. Мониторинг 24ч
        // Если кандидат превосходит baseline на >=5% -> продвинуть на 100%
        // Если отстаёт -> авто-откат
    }
}

13.7 Проекция на 2029: Распределённый Edge Publisher с Residential Proxy Farm

ПРОГНОЗИРУЕМАЯ ПРОБЛЕМА: Централизованная публикация не масштабируется

Почему это важно сейчас: При публикации с одного IP платформы (TikTok/YouTube/IG) начнут теневые баны уже при >100 видео/день. Rate limits (50-100 uploads/day per account) не позволят превысить 1K видео/день. OAuth токены истекают, и их ручное обновление станет узким местом.

Архитектурное решение: Закладываем Распределённую Edge Publisher Mesh с первого этапа проектирования: 10,000+ residential proxy узлов, автоматическая ротация браузерных отпечатков, шифрованное хранилище OAuth токенов с автообновлением, и детектор shadowban.
