3.1 LLM Provider Abstraction Layer

3.1.1 Архитектура уровня абстракции

3.1.2 Базовый интерфейс

// LLMProvider interface — каждый адаптер реализует этот контракт

interface LLMProvider {
  name: string
  models: Model[]

  generate(params: GenerateParams): Promise<GenerateResult>
  chat(params: ChatParams): Promise<ChatResult>
  embed(params: EmbedParams): Promise<EmbedResult>
  stream(params: ChatParams): AsyncIterable<StreamChunk>
  countTokens(text: string): number
  estimateCost(tokens: TokenUsage): number
}

interface Model {
  id: string                    // e.g. "gpt-4o", "claude-3-opus"
  capabilities: ModelCapability[]
  contextWindow: number
  maxOutputTokens: number
  costPer1KInput: number        // USD
  costPer1KOutput: number       // USD
  tier: 'free' | 'budget' | 'standard' | 'premium'
}

enum ModelCapability {
  TEXT_GENERATION, CHAT, CODE,
  IMAGE_GENERATION, IMAGE_UNDERSTANDING,
  VIDEO_GENERATION, AUDIO_GENERATION,
  EMBEDDINGS, FUNCTION_CALLING,
  STREAMING, VISION
}

3.2.2 Логика роутера

Роутер выбирает лучшую модель для каждого запроса на основе:

  1. Соответствие возможностям — модель должна поддерживать требуемую capability (чат, генерация изображений и т.д.)
  2. Проверка доступности — провайдер достижим? модель загружена?
  3. Приоритет — наименьший номер приоритета побеждает
  4. Бюджет — пропустить, если вызов превышает дневной лимит
  5. Балансировка — распределение между провайдерами с одинаковым приоритетом

3.2.4 Circuit Breaker

// Circuit breaker — предотвращает каскадные отказы

interface CircuitBreakerState {
  provider: string
  model: string
  failures: number
  lastFailure: timestamp
  state: 'closed' | 'open' | 'half-open'
  threshold: number         // отказов до открытия (по умолч.: 5)
  cooldown_ms: number       // время до half-open (по умолч.: 60000)
}

// Когда circuit OPEN:
//   → все запросы к этому провайдеру/модели немедленно отклоняются
//   → роутер выбирает следующую доступную модель/провайдера
// После cooldown:
//   → circuit → HALF-OPEN, разрешает 1 тестовый запрос
//   → успех → CLOSED (нормальная работа)
//   → отказ → OPEN снова (двойной cooldown)

3.4 Context & Memory System

3.4.1 Трёхуровневая архитектура памяти

◈ Ephemeral
Область: Один запуск пайплайна
Хранилище: In-memory (Python dict / Redis)
Хранение: Минуты (до завершения запуска)
◈ Short-term
Область: Текущий батч/сессия
Хранилище: Redis (TTL: 24ч)
Хранение: Часы — дни
◈ Long-term
Область: Все исторические данные
Хранилище: PostgreSQL + pgvector
Хранение: Месяцы — годы

3.4.2 Ephemeral Context (Pipeline Run)

Во время выполнения одного пайплайна агенты используют run context — объект, передаваемый через все 12 стадий. Это позволяет избежать избыточных LLM-вызовов и обеспечивает консистентность.

Хранит недавние взаимодействия и решения агентов для текущего батча. Используется для согласованности между видео в одной кампании.

agent:{agent_id}:rate_limit        → { "calls_this_minute": 12, "reset_at": ... }

3.4.4 Long-Term Memory (Vector Store)

Долговременная память использует pgvector для поиска по векторному сходству. Хранит:

  • Content embeddings — все сгенерированные сценарии, заголовки, описания
  • Performance memory — что сработало/не сработало с тегами по метрикам
  • Character consistency — описания персонажей, черты, история
  • World consistency — лор мира, правила, установленные факты
  • Style memory — успешные паттерны стилей, типы хуков, монтажные паттерны
// memory_entries (PostgreSQL + pgvector)

CREATE TABLE memory_entries (

3.5.3 Поиск и получение данных

// Функция поиска в памяти — используется всеми агентами

async function searchMemory(
  query: string,
  filters: {
    entry_types?: MemoryEntryType[]
    agent_id?: string
    tags?: string[]
    min_importance?: number
    max_age_days?: number
    platform?: string
    limit?: number
  }
): Promise<MemoryEntry[]> {
  const embedding = await embed(query)
  const results = await pgvector.query(`
    SELECT id, content, metadata,
           1 - (embedding <#> $1) AS similarity
    FROM memory_entries
    WHERE entry_type = ANY($2)
      AND ($3::text IS NULL OR agent_id = $3)
      AND ($4::text[] IS NULL OR tags && $4)
      AND importance >= $5
      AND (expires_at IS NULL OR expires_at > NOW())
    ORDER BY similarity DESC
    LIMIT $6
  `, [embedding, filters.entry_types ?? ALL,
       filters.agent_id, filters.tags,
       filters.min_importance ?? 0,
       filters.limit ?? 10])

  return results.map(r => ({
    ...r,
    score: r.similarity * r.importance
  }))
}

3.7.3 Стратегии оптимизации

1. Semantic Caching

Проблема: Похожие промпты порождают разные LLM-вызовы, хотя могут использовать кэшированные результаты.

Решение: Перед вызовом LLM — вычислить эмбеддинг промпта и найти похожие результаты (cosine similarity > 0.95).

Ожидаемый эффект: 15-30% снижение API-вызовов.

2. Prompt Compression

Проблема: Длинный контекст с memory injection потребляет 4K+ токенов на вызов.

Решение: Перед отправкой к платным API — сжать промпт через LLMLingua. Для локального Ollama сжатие пропускается.

Ожидаемый эффект: 40-60% снижение входных токенов для платных провайдеров.

3. Model Tiering

Проблема: Все задачи используют одну модель независимо от сложности.

Решение: Классификация промптов по сложности:

  • Простые (генерация хэштегов, варианты заголовков) → mistral:7b
  • Средние (сценарии, описания) → llama3:70b
  • Сложные (creative direction, стратегия, оптимизация) → GPT-4o/Claude 3.5

Ожидаемый эффект: 50-70% снижение стоимости.

4. Batch Processing

Проблема: Индивидуальные LLM-вызовы имеют высокий overhead на токен.

Решение: Для неинтерактивных этапов — батчинг нескольких промптов в один LLM-вызов.

Ожидаемый эффект: 60-80% снижение API-вызовов.

    with tracer.start_as_current_span("llm.generate") as span:
        span.set_attribute("llm.provider", provider.name)
        span.set_attribute("llm.model", model.id)
        span.set_attribute("llm.agent", agent_id)
        span.set_attribute("llm.prompt_length", len(prompt))
        span.set_attribute("llm.temperature", params.temperature)

        try:
            result = await provider.generate(params)
            elapsed = time.monotonic() - start

            span.set_attribute("llm.latency_ms", elapsed * 1000)
            span.set_attribute("llm.input_tokens", result.usage.input_tokens)
            span.set_attribute("llm.output_tokens", result.usage.output_tokens)

        except Exception as e:

            span.set_status(trace.StatusCode.ERROR, str(e))

3.9.2 L1 — Exact Match Cache

// L1 — точное совпадение промпта, in-memory, для дедупликации в батче

class ResponseCacheL1:
    def __init__(self):
        self._cache: dict[str, CacheEntry] = {}
        self._max_size = 1000
        self._ttl_ms = 300_000  # 5 минут

    async def get(self, key: str) -> str | None:
        entry = self._cache.get(key)
        if entry and (time.monotonic() - entry.timestamp) < self._ttl_ms:
            entry.access_count += 1
            return entry.value
        return None

    async def set(self, key: str, value: str):
        if len(self._cache) >= self._max_size:
            oldest = min(self._cache.items(), key=lambda x: x[1].access_count)
            del self._cache[oldest[0]]
        self._cache[key] = CacheEntry(value=value, timestamp=time.monotonic())

    def make_key(self, provider: str, model: str, prompt: str, temperature: float):
        normalized = prompt.strip().lower()
        return f"{provider}:{model}:{hash(normalized)}:{temperature}"

3.9.3 L2 — Semantic Cache

// L2 — семантическое сходство: "тот же смысл, другие слова"

class SemanticCache:
    similarity_threshold = 0.95
    max_results = 1

    async def get(self, prompt: str, agent_id: str) -> str | None:
        embedding = await embed(prompt)
        results = await pgvector.query(`
            SELECT response, 1 - (prompt_embedding <#> $1) AS similarity
            FROM semantic_cache
            WHERE agent_id = $2
              AND created_at > NOW() - INTERVAL '24 hours'
              AND 1 - (prompt_embedding <#> $1) > $3
            ORDER BY similarity DESC
            LIMIT 1
        `, [embedding, agent_id, self.similarity_threshold])
        if results:
            return results[0].response
        return None

    async def set(self, prompt: str, response: str, agent_id: str):
        embedding = await embed(prompt)
        await pgvector.query(`
            INSERT INTO semantic_cache (prompt_hash, prompt_text, prompt_embedding,
                                         response, agent_id, created_at)
            VALUES ($1, $2, $3, $4, $5, NOW())
            ON CONFLICT (prompt_hash) DO UPDATE
            SET access_count = semantic_cache.access_count + 1,
                last_access = NOW()
        `, [hash(prompt), prompt[:500], embedding, response, agent_id])

3.9.4 Правила инвалидации кэша

  • Автоматическая: L1 каждые 5 мин, L2 каждые 24ч, L3 после 30 дней
  • При изменении шаблона: инвалидация всех кэшей для этого агента
  • При смене модели: разные модели → разные результаты (кэш модель-специфичен)
  • Ручная: Админ может сбросить кэш per-agent или глобально через дашборд
  • Селективная: Результаты с низким performance авто-истекают

3.10.2 Паттерны отказоустойчивости

Timeout с graceful degradation

Каждый LLM-вызов имеет таймаут (по умолч.: 30s для чата, 60s для генерации, 120s для изображений). При таймауте:

  1. Повтор с увеличенным таймаутом (+50%)
  2. Failover на следующую модель (потенциально меньше/быстрее)
  3. Если все модели отказали — шаблонный ответ
  4. Пометить этап пайплайна на проверку, перейти к следующему видео

Частичный успех пайплайна

При сбое этапа в середине пайплайна система может:

  • Повторить этап (до 3 раз)
  • Пропустить этап, если он некритичен
  • Использовать fallback (стоковые кадры вместо генерации)
  • Абортить видео, записать ошибку, перейти к следующему
Видео со сбоем сохраняется как failed pipeline run с диагностикой.

Health Checks провайдеров

Каждые 30 секунд health check проверяет провайдеров:

  • Ollama: GET /api/tags — сервер работает, модели загружены
  • OpenAI/Anthropic: GET /v1/models — API ключ и связь
  • ComfyUI: GET /system_stats — очередь и GPU память
Нездоровые провайдеры удаляются из пула маршрутизации до восстановления.
