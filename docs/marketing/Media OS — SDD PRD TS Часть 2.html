05 REST API Design

5.1 Конвенции API

КонвенцияЗначение
Base URL/api/v1
ПротоколHTTPS only (HTTP редирект в production)
ФорматJSON (application/json)
АутентификацияBearer JWT (Authorization: Bearer <token>) или API Key (X-API-Key: <key>)
ПагинацияCursor-based (cursor + limit) для списков, offset-based для admin
ОшибкиСтандартный error envelope: {"error": {"code": "...", "message": "...", "details": {...}}}
УспехСтандартный response: {"data": {...}, "meta": {...}}
Rate limiting100 req/min на пользователя, 1000 req/min на API key
ВерсионированиеURL path versioning (/api/v1/...)

5.2 Стандартный Response Envelope

Успешный ответ:
{
  "data": { ... },
  "meta": {
    "request_id": "uuid",
    "timestamp": "2026-07-24T12:00:00Z",
    "pagination": { "cursor": "next_cursor_string", "has_more": true, "limit": 20 }
  }
}

Ответ с ошибкой:
{
  "error": {
    "code": "validation_error",
    "message": "Некорректное поле: title должно быть от 1 до 300 символов",
    "details": { "field": "title", "reason": "too_long", "constraint": { "max_length": 300 } },
    "request_id": "uuid"
  },
  "meta": { "request_id": "uuid", "timestamp": "2026-07-24T12:00:00Z" }
}

5.4 Поток Аутентификации

JWT AUTH FLOW:
1. Клиент -> POST /api/v1/auth/login { email, password }
2. Сервер проверяет -> возвращает { access_token, refresh_token, expires_in: 3600 }
3. Клиент отправляет: Authorization: Bearer jwt...
4. Защищённые эндпоинты проверяют: подпись JWT, срок, активность, роли
5. При 401: POST /api/v1/auth/refresh { refresh_token } -> новый access_token

API KEY AUTH FLOW:
1. Пользователь создаёт ключ в настройках (показывается ОДИН РАЗ: "ak_aion_xyz...")
2. В БД хранится SHA-256 хэш
3. Клиент: X-API-Key: ak_aion_xyz...
4. Сервер хэширует и сверяет. API ключи имеют scope-ограничения (read/write/publish)

5.5 Детали Пагинации

Все list-эндпоинты используют cursor-based пагинацию. Кодирование курсора: base64(json_encode({"next_id": last_uuid, "next_sort": last_sort_value})).

Запрос:  GET /api/v1/projects?cursor=eyJpZCI6ICJ1dWlkIn0=&limit=20
Ответ:  { "data": [...], "meta": { "pagination": { "cursor": "...", "has_more": true, "limit": 20 } } }

06 AI Agents System

6.1 Обзор Архитектуры Агентов

Архитектура AI Агентов

Каждый агент — это Python-сервис, который потребляет задачи из выделенной Redis-очереди, обрабатывает их с использованием локальных AI-моделей (Ollama/ComfyUI) и передаёт результат в очередь следующего агента. Агенты — stateless-воркеры, которые могут горизонтально масштабироваться.

АРХИТЕКТУРА АГЕНТА (каждый агент):

+-------------------------------------------------------+
|                    AGENT WORKER                        |
|                                                        |
|  Redis -> Consumer (listen) -> deserialize payload     |
|                                     |                  |
|                                     v                  |
|                            +------------------+        |
|                            |   Agent Logic     |        |
|                            |  (LLM / ComfyUI / |        |
|                            |   FFmpeg / API)   |        |
|                            +--------+---------+        |
|                                     |                  |
|                          +----------+----------+       |
|                          v                     v       |
|                   +------------+     +------------+    |
|                   |  Store     |     |  Enqueue   |    |
|                   |  Result    |     |  Next Job  |    |
|                   |  (DB+MinIO)|     |  (Redis)   |    |
|                   +------------+     +------------+    |
+-------------------------------------------------------+

КОММУНИКАЦИЯ: Все агенты общаются ТОЛЬКО через Redis-очереди.
Никаких прямых HTTP-вызовов между агентами. Слабое связывание и надёжность.
Ключевой принцип: Агенты не знают о существовании друг друга. Каждый читает из своей очереди, обрабатывает и пишет в следующую. Оркестрация — через конфигурацию маршрутизации событий.

6.2 Определения Агентов

🎯
Creative Director
Активен
Очередь: pipeline:concept
Модель: Qwen2.5 7B (Ollama)
Тип: LLM · Генерация идей

Роль: Главный креативный стратег. Генерирует идеи контента на основе seed-тем, трендов и бренд-гайдлайнов.

Вход
{ "project_id", "seed_topic", "count": 5, "style", "target_audience", "trending_signals" }
Выход
[{ "title", "description", "hook", "emotional_appeal", "format_suggestion", "trending_score" }]
Алгоритм
  1. Получить трендовые темы от Analytics Agent
  2. Собрать промпт с инструкциями + трендами + seed-темой
  3. Вызвать LLM со структурированным JSON выводом
  4. Валидировать JSON-схему, оценить трендовый потенциал
  5. Сохранить в ideas table -> поставить лучшие в очередь screenwriter
✍️
Screenwriter
Активен
Очередь: pipeline:script
Модель: Qwen2.5 7B (Ollama)
Тип: LLM · Сценарии

Роль: Преобразует идеи в полноценные видео-сценарии с диалогами, озвучкой и структурой сцен.

Вход
{ "project_id", "idea_id", "concept", "format_type", "target_duration_seconds", "character_ids", "world_id" }
Выход
{ "title", "format", "full_text", "voiceover_text", "scene_count", "key_lines", "cta_text", "hashtag_suggestions", "word_count", "emotional_arc" }
Алгоритм
  1. Загрузить идею + конфиг проекта (персонажи, мир, стиль)
  2. Контроль длительности: для 30s видео ~60-80 слов, 3-5 сцен
  3. Вызвать LLM с JSON-разбивкой по сценам
  4. Валидировать: количество слов, сцен, наличие хука и CTA
  5. Сохранить сценарий -> поставить в очередь storyboard

Video Editor (FFmpeg)
Активен
Очередь: pipeline:edit
Модель: FFmpeg + Python (moviepy)
Тип: CPU · Композиция видео

Роль: Собирает финальное видео из клипов, изображений, аудио, субтитров и эффектов.

Вход

Выход
{ "url", "thumbnail_url", "duration_seconds", "resolution", "fps", "has_voiceover", "subtitles_url" }
Алгоритм
1. Загрузить клипы/изображения из MinIO
2. Если нужна озвучка: Coqui TTS из voiceover_text + character voice config

4. Построить FFmpeg filter_complex: склейка + crossfade + оверлеи + субтитры + аудио (duck) + интро/аутро
5. Рендеринг -> обложка (25% кадр + title overlay) -> загрузить в MinIO -> сохранить -> publish очередь

6.4 Стратегия Prompt Engineering

Все LLM-агенты используют общий фреймворк промптов:

КомпонентОписание
System MessageОпределяет роль, тон, ограничения. Статичен для каждого типа агента.
Context InjectionДинамический: проект, персонажи, мир, тренды, прошлые результаты.
Task InstructionЧёткие пошаговые инструкции со спецификациями формата.
Few-Shot Examples2-3 примера идеального вывода из исторически успешного контента.
Structured Output SchemaJSON-схема, которой вывод ОБЯЗАН соответствовать. Валидация после генерации.
ConstraintsЛимиты длины, правила тона, бренд-гайдлайны, правила платформ.
Chain of ThoughtДля сложных рассуждений: шаг за шагом перед финальным ответом.

6.5 Паттерн Реализации Воркера

Базовый паттерн Python-воркера для всех агентов:

Base Worker Pattern (Python):

class BaseAgent:
    def __init__(self):
        self.redis = redis.from_url(settings.REDIS_URL)
        self.db = Database()
        self.minio = MinioClient()

    def run(self):
        while True:
            msg = self.redis.brpop(self.queue_name, timeout=30)
            if not msg: continue
            job = json.loads(msg[1])
            try:
                self._update_job(job['job_id'], 'processing')
                result = self.process(job)
                self._store_result(job, result)
                self._enqueue_next(job, result)
                self._update_job(job['job_id'], 'completed')
            except RetryableError as e:
                self._handle_retry(job, e)
            except FatalError as e:
                self._handle_fatal(job, e)

    def process(self, job):
        raise NotImplementedError
